# 并行测速与全局延迟规则验收

## 实现行为

- 同地区全部候选节点同时开始测速，取消每批 4 个的限制；地区之间继续按既定顺序依次尝试。
- 候选测速、当前节点定时检测、切换前复核和切换后验证共用延迟规则：成功响应不超过 800 ms 即通过；首次超过时立即复测同一地址，两次均超过即视为节点超时。复测通过时采用第二次延迟。
- 当前节点的两个探测地址分别判断，任一通过即健康；取消并等待其他地址的请求及复测结束。两地址均未通过且存在已确认高延迟时，首轮检查即可启动恢复；普通请求失败仍需两轮确认。
- 候选节点确认高延迟后，本恢复轮直接排除。主地址无通过节点时，备用地址仅重试请求失败的节点；下一恢复轮重新允许全部节点参与。
- 进度按节点数统计；停止或应用地区设置会取消并等待所有初次测速及复测任务。现有地区选择、优先级与恢复后完整 10 秒冷却保持有效。

- macOS：读取到 4 个地区、35 个已识别节点，当前代理通过，合格延迟 240 ms。
- Windows 初次检查：读取到 6 个地区、53 个已识别节点；实际代理请求失败，结果为 `RequestFailed`。此前的 1.3.0 发布程序对同一节点同样失败。后续排查与恢复结果见下节。

## Windows 连接问题排查与恢复

- 原订阅 `Liangxin` 初始选择为“🇯🇵日本专线03|BGP|流媒体”，新旧发布版探针均失败。Windows `curl` 经该路径访问 HTTP 返回 502，HTTPS 握手失败或超时；直连 Cloudflare 可返回 204。
- 实际运行 `ProxyMonitor` 恢复：日本全部节点并行测速，测速最快的高速04实际验证失败后自动尝试高速01。高速01曾通过检查，但后续仍有请求失败和连续高延迟，不能视为稳定恢复。高速02的六次实际检查均未通过。
- 固定日本节点和地址对比默认 TLS、TLS 1.2 与 TLS 1.3，三种模式均有正常响应和慢响应；到本地 Clash 的连接正常，延迟集中在后续握手。香港线路的六次临时对照检查全部通过，结束后恢复日本选择。证据指向原订阅的日本路径问题。
- 用户明确要求仅保留日本地区。最终切换到 Windows 中已有的 `me` 订阅，选择“日本6-A1”，并通过应用设置存储保存恢复列表 `["JP"]`。当前为全局模式、7890 端口，识别到 4 个地区、35 个节点、2 个未识别条目。
- 日本6-A1连续六次实际检查通过，延迟依次为 194、158、304、157、162、155 ms；独立启动发布版程序再检查三次，分别为 194、201、193 ms；生产监控器按 10 秒间隔再检查三次，分别为 204、175、169 ms。合计 12 次全部通过，范围 155–304 ms。
- NuGet 在线漏洞查询和锁定还原通过。修复发生在远程 Clash 的订阅与节点配置；全局 800 ms 判定继续生效，所有真实恢复验证仅运行代理监控器。
- 原订阅仍在 Clash 中；切换前配置备份保存在远程 `D:\clash-party-windows-1.8.9-x64-portable\data\profile.yaml.before-watchdog-a1.bak`。临时诊断程序与计划任务在验收后清理。
